## The round's own story: three defects between this repo and a check that could run

All three had produced greens that meant nothing, and each was fixed in-tree.

1. **The check verb was never served.** The SDK asks the provider whether it also implements `kit.CheckVerbProvider`; mine did not, because `RunVerb` lived on a separate type. Fixed with the org's two-class shape (`plugin-qdrant` is the reference): one type serves both, and the verb capability declares `Primary: "method"`.
2. **`Invoke` never dispatched on `req.GetClass()`** — so a *verb* invocation ran the *command* effect, exited non-zero, and reported `firecracker: command exited 1` with no message. **No `firecracker:` check of this plugin had ever executed.** Now `classVerb → invokeVerb`, which decodes the full `spec.Op`, rebuilds the venue context with `sdk.NewCheckContext(req.GetExecutorBrokerId(), req.GetEnvJson())`, and runs the SAME core verb.
3. **The probe claimed a read-back the API does not implement.** Measured against a real v1.17: `GET /` and `GET /machine-config` answer and `GET /mmds` returns the tree, while `GET /boot-source`, `GET /drives/<id>` and `GET /network-interfaces/<id>` are **400 `Invalid request method and/or path`**. So a healthy VMM failed every run. Documents with no readable endpoint are now proven by their **accepted write** (204, asserted per document, with the VMM's own fault body on refusal) and the configuration by the document the API serves back, as a **subset** — the VMM owns fields of its own (`track_dirty_pages`, `huge_pages`).

4. **The Go client still read back `GET /boot-source`** — the endpoint this PR had measured as 400 — so a real `launch`/`configure` failed every time, while the *probe's* scripts (a separate implementation) were what the bed actually exercised. Worse, `fakeVMM` **answered that GET**, so the double agreed with the wrong assumption instead of the API. Fixed: documents with no readable endpoint are proven by their accepted write, and the double now answers **400** with the real fault message — so it can never again certify a wrong assumption, which also turned the existing sequence test into the regression gate it should always have been.
5. **The `doctor` invented a problem** when no snapshotter was configured: with an empty name no row matches, so it reported *"the daemon does not serve a snapshotter named \"\" at all"* — failing a host that configured none. Now guarded, with a gate for that path.

Also fixed: the probe was host-local rather than venue-aware; a `run:` fixture in the bed's plan can **never** satisfy a check there, because `charly check live` is verify-only by design and marks mutating steps `skipped — verify-only mode (mutating step)` (measured against a freshly created target, which corrected a wrong first diagnosis of a stale VM) — the probe owns and *measures* its scratch fixture; metadata now requires an interface at both ends.

## What this PR deliberately does NOT claim

A **booted guest** needs a root drive that is a real filesystem; that producer is filed as **opencharly/plugin-firecracker#1**, and until it lands `launch` requires a rootfs you supply and nothing claims a guest came up. The bed also does not assert the `doctor`'s **verdict**: the doctor answers "can this host run a POOL", which needs a containerd daemon serving a root-drive-capable snapshotter — a property of a pool host, not of a disposable guest. Its snapshotter probe is covered by a unit gate pinned to the real `ctr plugins ls` output, and that probe's live path did not execute in the reported run (the cited permission-denied dial returns before it).
